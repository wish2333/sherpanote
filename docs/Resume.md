### 1.1 项目背景

在研究生阶段的课程学习和教育实习中，我发现学生群体面临一个普遍痛点：学习资料的记录和整理过程极其低效。具体表现为三个方面：一是课堂和在线课程录音，传统的做法是先录音再手动回听逐字整理，一次两小时的讲座往往需要额外花费两三个小时处理笔记；二是论文参考文献、扫描件书籍和不可复制的在线文档（如部分知网、百度文库页面），文字提取只能靠手动逐字录入或截图后手动抄写；三是学习笔记的版本管理混乱，反复修改后无法回溯历史内容。

市面上的工具要么功能单一（只录音或只转录），要么依赖云端服务（隐私和费用问题），要么只支持英文场景。我希望构建一款"一站式"学习记录工具：从语音采集、实时转录、文档OCR提取、AI辅助整理到版本管理和多格式导出，全部在本地完成，同时支持中英文等多种语言。SherpaNote 由此诞生。

### 1.2 用户画像

- **主要用户**：同专业的研究生同学、实习期间的教育工作者、学习小组伙伴
- **使用场景**：
  - **语音转录**：课堂录音转录、在线课程（慕课、B站课程）音频提取与文字化、讲座内容整理、研究访谈记录
  - **文档提取**：论文PDF的文字层提取、扫描件书籍OCR识别、不可复制的在线文档截图转文字、课件PPT内容提取
  - **AI辅助整理**：课程笔记结构化整理、复习备考思维导图生成、文献综述头脑风暴
  - **版本管理**：论文写作过程中的多版本快照与回溯、笔记迭代修改记录
- **现有工具的不足**：语音识别依赖云端（隐私顾虑）、OCR工具不支持批量处理和PDF文字层自动检测、笔记软件缺乏版本管理、各工具之间数据不互通、扫描件和受保护文档没有便捷的文字提取手段

## 2. 痛点与动机

### 使用前的痛点

- **转录效率低**：两小时讲座或在线课程录音需要2-3小时手动整理文字，整体时间成本翻倍
- **文档提取困难**：论文PDF部分为扫描件无法复制、在线文档（知网预览、百度文库）限制文字选取、参考书籍只有纸质版或扫描版，这些场景下获取文字只能手动录入，一份20页的文献可能要花半天时间
- **工具碎片化**：录音、转录、OCR、笔记整理分散在4-5个不同应用中，数据流转靠手动复制粘贴
- **隐私与成本**：主流语音识别和AI处理服务均为云端方案，研究访谈等敏感内容不适合上传第三方服务器，且按量计费成本不低
- **中文支持差**：多数开源ASR工具以英文为主，中文识别精度和模型选择有限
- **文档处理割裂**：图片OCR、PDF文字提取、Office文档处理需要不同软件，无法统一管理，且多数OCR工具无法自动区分PDF是否有文字层

### 使用后的改善

- **转录效率提升约70%**：实时流式转录将"录音后处理"变为"边说边出文字"，AI润色/笔记生成将后续整理时间从小时级压缩到分钟级
- **文档提取效率提升约80%**：扫描件书籍、不可复制文档截图、论文PDF等以往需要半天手动录入的内容，通过拖拽导入即可在数分钟内完成文字提取
- **一站式工作流**：从语音采集到AI处理到多格式导出，全流程在单一应用内完成
- **完全本地运行**：语音识别（sherpa-onnx）和OCR（RapidOCR）均在本地执行，仅AI文本处理需调用OpenAI兼容API，敏感数据不离开用户设备
- **多语言覆盖**：支持14种语言，包括中文、英文、日文、韩文、粤语等，10+ASR模型可供选择
- **统一文档处理**：图片、PDF、Office文档均可在同一界面通过拖拽完成识别和文字提取，PDF自动检测文字层避免不必要的OCR

## 4. 产品方案

### 4.1 方案概述

SherpaNote 的核心价值是"本地优先的语音-文字-AI一体化学习工具"。产品围绕"采集-转录-整理-管理"四个环节构建了完整的工作流：

- **采集层**：麦克风实时录音、音频/视频文件导入、图片/PDF/Office文档拖拽导入
- **处理层**：本地ASR引擎（10+模型可选）、本地OCR引擎、云端AI文本增强
- **整理层**：4种AI处理模式（润色、笔记、思维导图、头脑风暴）、自定义AI预设
- **管理层**：SQLite本地存储、版本快照、全文搜索、多格式导出

### 4.2 核心功能设计

#### 功能一：实时流式语音转录

- **解决的问题**：课堂录音和在线课程视频（慕课、B站课程等）的转录效率极低，两小时课程需要额外数小时手动整理
- **方案设计**：基于sherpa-onnx构建双模式转录引擎：流式识别提供实时反馈，离线识别处理已有音频文件。针对仅支持离线模式的模型（如SenseVoice、Qwen3-ASR），创新性地设计了"模拟流式"管线 -- VAD语音分段 + 离线识别 + 逐段推送，统一了所有模型的实时显示体验。支持10+ASR模型覆盖14种语言，包括对中文优化较好的Paraformer和Qwen3-ASR
- **关键技术决策**：选择sherpa-onnx而非Whisper.cpp作为默认引擎，核心考量是中文场景的支持深度 -- sherpa-onnx原生支持Paraformer、Qwen3-ASR等中文优化模型，且ONNX Runtime的跨平台兼容性优于Whisper.cpp的native binary方案。同时保留Whisper.cpp作为可选后端，满足需要特定硬件加速（如CUDA GPU）的用户

#### 功能二：AI驱动的文本处理

- **解决的问题**：原始转录文本质量参差不齐（口语化、无结构），学生需要额外大量时间进行人工整理和格式化
- **方案设计**：通过OpenAI兼容API提供四种处理模式，精准匹配不同学习场景：润色模式用于课堂录音的语句优化，笔记模式用于研究访谈的结构化整理，思维导图模式用于复习备考的知识体系可视化，头脑风暴模式用于论文写作的思路扩展。所有模式均采用流式输出，用户可实时看到生成过程而非面对空白等待
- **关键技术决策**：采用OpenAI兼容API标准而非绑定特定供应商。这意味着用户可以在OpenAI、OpenRouter、本地部署的Ollama或任何兼容端点之间自由切换，避免供应商锁定。同时实现了自定义AI预设系统，支持多供应商API配置和用户自定义处理模板

#### 功能三：多后端文档提取

- **解决的问题**：论文扫描件、受保护在线文档截图、参考书籍照片等场景下，获取文字只能手动录入，效率极低；且不同类型文件的最佳处理方式差异很大，单一引擎无法兼顾所有场景
- **方案设计**：设计智能决策树进行文件路由 -- 图片走PP-OCR进行文字识别，Office文件（DOCX/PPTX/XLSX）走markitdown直接提取，PDF先通过pdfplumber检测是否存在文字层，有文字层则直接提取，无文字层（扫描件）则转换为图片后OCR。对于提取质量要求更高的场景，可选安装docling（高级布局分析）和opendataloader-pdf（基于Java的专业PDF解析）两个高级后端
- **关键技术决策**：高级后端采用子进程隔离的插件架构。核心考量是依赖隔离：docling依赖PyTorch等大型库（约2GB），opendataloader-pdf需要Java运行时，直接集成会导致主程序体积膨胀5-10倍且引入依赖冲突风险。插件在独立Python虚拟环境中通过uv管理，通过base64编码JSON参数 + JSON Lines进度事件的IPC协议通信，实现一键安装/卸载

#### 功能四：版本历史与数据管理

- **解决的问题**：学生在反复修改笔记和论文草稿时需要回溯历史版本，传统笔记软件要么不支持版本管理，要么用布尔标记"当前版本"导致状态不一致
- **方案设计**：采用内容差异脏检测替代布尔标记 -- 每次保存时对比当前内容与最新版本的哈希值，仅在实际内容变化时才创建新版本快照，避免无意义的重复保存。SQLite WAL模式保证并发读写安全，FTS5全文搜索支持跨记录的关键词检索，多格式导出（Markdown、TXT、DOCX、SRT）满足不同下游场景需求

### 4.3 系统架构

```
┌─────────────────────────────────────────────────────┐
│                   Vue 3 Frontend                     │
│   (TypeScript + Pinia + Tailwind CSS 4 + DaisyUI 5) │
│   bridge.ts: call() / onEvent() 双向通信             │
└──────────────────────┬──────────────────────────────┘
                       │ pywebview JS-Python Bridge
┌──────────────────────┴──────────────────────────────┐
│              Python Backend (Mixin架构)               │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐             │
│  │ AsrMixin │ │ AiMixin  │ │StorageMix│             │
│  └──────────┘ └──────────┘ └──────────┘             │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐             │
│  │ModelsMix │ │OcrPlugin │ │ConfigBak │             │
│  └──────────┘ └──────────┘ └──────────┘             │
└─────────────────────────────────────────────────────┘
     │              │               │
  sherpa-onnx    OpenAI API      SQLite
  RapidOCR     (兼容端点)        (WAL模式)
  markitdown
  docling(*)     opendataloader(*)
  (*插件子进程隔离)
```

- **前端**：Vue 3 + TypeScript，单Pinia Store管理全局状态，Composable模式拆分领域逻辑
- **后端**：Python 3.11+，SherpaNoteAPI通过6个领域Mixin类组合，每个Mixin专注一个业务域
- **通信**：非HTTP REST，而是pywebview原生JS-Python桥。线程安全的消息队列解决Windows COM/WebView2的线程限制
- **数据库**：SQLite WAL模式 + FTS5全文搜索，所有数据和配置本地持久化
- **插件系统**：子进程隔离 + uv虚拟环境管理，base64编码JSON参数传递，JSON Lines进度事件流

## 5. 开发过程

### 5.1 规划与调研阶段（2026年4月初）

在正式编码前，我花了一周时间进行需求梳理和技术调研：

- **需求梳理**：通过观察5位同学和实习同事的日常学习习惯，结合自身体验，梳理出三大核心需求场景：(1)语音转录 -- 课堂和在线课程录音的自动文字化；(2)文档提取 -- 论文PDF、扫描件书籍、受保护在线文档的文字获取；(3)AI辅助整理 -- 转录/提取后的原始文字需要结构化处理（笔记、思维导图等）。据此确定MVP优先级：语音转录 + AI处理为P0，OCR和文档提取为P1后续迭代
- **ASR引擎选型**：对比了Whisper、sherpa-onnx、Vosk、FunASR四个方案。sherpa-onnx在中文支持（原生支持Paraformer、Qwen3-ASR等中文优化模型）、模型丰富度（10+模型覆盖14种语言）和本地部署便捷性（ONNX Runtime跨平台）上综合最优
- **桌面框架选型**：评估了Electron、Tauri、Qt和pywebview。考虑到后端需要直接调用Python ML库（sherpa-onnx、RapidOCR），pywebview + Vue的组合让Python后端和Web前端在同一进程中通信，避免了Electron方案下Python-Node.js跨进程桥接的复杂性
- **PyWebVue框架搭建**：pywebview本身只提供窗口和JS桥，缺乏结构化的通信框架。我需要自建事件队列、线程安全机制和装饰器API暴露层，形成了可复用的PyWebVue框架

### 5.2 MVP实现（v1.0.0，2026年4月8日-9日）

用两天时间完成了核心MVP：

- 实现PyWebVue桥接框架（@expose装饰器 + _emit事件机制）
- 集成sherpa-onnx实现流式/离线两种转录模式
- 搭建SQLite存储层（CRUD + FTS5搜索 + 版本历史）
- 对接OpenAI兼容API实现4种AI处理模式
- 完成5个基础视图（首页、录音、编辑器、设置、音频管理）
- 实现多源模型管理（GitHub、HuggingFace等5种下载源）

MVP完成后邀请同专业3位同学和实习期间2位同事试用，收集到以下关键反馈：

- **模型需求多样化**：不同同学的语言背景不同（一位需要粤语支持，一位经常处理英文课程），仅Paraformer中文模型不够用，需要更多语言和模型选择 -> 直接推动了v1.1.0新增6个ASR模型和多语言支持
- **离线模型无实时反馈**：有同学下载了SenseVoice模型但发现只有离线模式，录音时看不到实时文字，体验明显不如流式模型 -> 触发了"模拟流式识别"管线的开发
- **长录音处理慢**：一位同学尝试转录2小时的完整讲座录音，CPU转录耗时较长，询问是否有GPU加速方案 -> 推动了v1.3.0的CUDA支持和whisper.cpp集成
- **有视频转录需求**：实习同事希望直接从慕课视频提取文字，不想手动导出音频再导入 -> 推动了yt-dlp视频下载和ffmpeg音频提取功能
- **UI交互问题**：音频播放使用file://协议在某些情况下失败、转录结果未自动保存、AI处理完切换页面后结果丢失 -> 这些问题在后续版本中逐个修复

## 7. 亮点与挑战

### 7.1 技术挑战

- **挑战一：Windows DLL冲突**
  - **问题**：ONNX Runtime和WebView2在Windows上都依赖特定版本的C++运行时DLL，若pywebview先加载WebView2，再导入sherpa-onnx会导致DLL冲突崩溃
  - **解决方案**：在main.py入口处、pywebview初始化之前，强制预导入sherpa_onnx模块，确保ONNX Runtime DLL先于WebView2加载
  - **收获**：深入理解了Windows DLL加载顺序和进程内存布局，掌握了桌面应用中多运行时共存的解决策略

- **挑战二：跨线程通信的COM限制**
  - **问题**：Windows上WebView2基于COM模型，后台线程无法直接调用evaluate_js，导致ASR进度事件和AI流式响应无法推送至前端
  - **解决方案**：设计线程安全的事件队列系统：后台线程将事件推入队列，JS端50ms定时轮询flush_events()批量处理，通过CustomEvent分发到各组件
  - **收获**：掌握了跨线程GUI更新的经典模式，理解了事件驱动架构在桌面应用中的重要性

- **挑战三：主动跨平台适配（macOS）**
  - **背景**：开发环境为Windows，但目标用户中包含macOS用户。在v1.0.0发布前，我主动进行macOS兼容性验证和适配，而非等用户报bug
  - **问题**：macOS上发现三类兼容性问题：(1)麦克风权限 -- macOS WebView需要Info.plist中声明NSMicrophoneUsageDescription，否则录音静默失败；(2)音频采样率 -- macOS AudioContext默认44100/48000Hz，而ASR模型要求16000Hz，需要增加重采样逻辑；(3)AudioContext suspended -- macOS Safari/WebView2在用户交互前会暂停AudioContext，需要添加重试机制和静音检测
  - **解决方案**：为macOS .app包添加Info.plist麦克风权限声明；实现AudioContext采样率自动重采样（44100/48000->16000）；添加3次重试的AudioContext恢复逻辑和3秒RMS<0.01的静音检测告警；针对macOS .app bundle特殊的目录结构适配模型路径检测
  - **收获**：在没有Mac设备的情况下，通过文档研究和代码审查完成了macOS兼容性适配，培养了跨平台开发的意识和系统性思维

- **挑战四：插件子进程隔离**
  - **问题**：docling依赖PyTorch等大型库，opendataloader-pdf依赖Java运行时，直接集成会导致主程序体积膨胀和依赖冲突
  - **解决方案**：设计子进程隔离的插件架构：每个插件在独立Python虚拟环境中运行，通过base64编码的JSON CLI参数传递输入，stdout返回结果，stderr传递JSON Lines格式进度事件。使用python-build-standalone + uv实现自包含的插件运行时
  - **收获**：实践了进程隔离和IPC通信设计，理解了如何在保持主程序轻量的同时支持可选重量级依赖

### 7.2 设计亮点

- **文档提取决策树**
  - 根据文件类型（图片/Office/PDF）和PDF文字层检测结果，自动路由到最优处理引擎。避免了一种引擎处理所有文件类型导致的效果不佳问题
- **模拟流式识别**
  - 对于仅支持离线模式的ASR模型，创新性地实现VAD分段 + 离线识别 + 逐段推送的管线，使用户获得与原生流式模型一致的实时反馈体验
- **不可变配置架构**
  - 所有配置对象使用frozen dataclass，更新时创建新实例而非修改现有实例，从根源避免了共享状态导致的并发问题和难以追踪的副作用
- **主动跨平台适配**
  - 在Windows开发环境下，主动完成了macOS的完整兼容性适配（麦克风权限、音频采样率、.app包目录结构），而非被动等待用户报bug。这体现了对跨平台开发的系统性考虑 -- 在发布前就预判了不同平台的差异点

### 7.3 开发过程亮点

- **VibeCoding开发模式**：充分利用AI编程助手加速开发流程。在技术选型、架构设计、代码实现和问题排查各阶段，AI助手帮助我将学习新技术和实现功能的时间大幅缩短。例如sherpa-onnx API集成、PyInstaller打包配置等通常需要数天摸索的工作，在AI辅助下数小时内完成
- **快速迭代周期**：平均每周发布一个新版本，每个版本都包含用户反馈驱动的功能改进和bug修复
- **用户驱动迭代**：每个新功能发布后邀请同学试用，收集具体使用场景和改进建议，确保开发方向与真实需求一致

## 8. 项目复盘

### 做得好的方面

- **本地优先的技术路线**：选择sherpa-onnx和RapidOCR等本地引擎作为核心，解决了隐私问题和离线使用需求，这是区别于云端工具的核心竞争力
- **渐进式架构演进**：从单体API逐步拆分为Mixin架构，每次重构都有明确的触发原因（代码膨胀、维护困难），避免了过度设计
- **插件化扩展思路**：将重量级可选依赖（docling、opendataloader）设计为按需安装的插件，保持了主程序的轻量性

### 可改进的方面

- **测试覆盖不足**：项目以手动测试为主，缺乏自动化测试。后期bug修复（特别是跨平台兼容性问题）耗费了较多时间，如有自动化测试可更早发现回归问题
- **错误处理完善度**：早期版本的错误处理不够完善，v2.1.1专门用一整个版本来修复静默错误吞没问题，说明应在开发初期就建立完善的错误处理规范

### 核心收获

- **端到端的产品能力**：从需求发现、技术选型、架构设计到编码实现和用户反馈，完整经历了一个桌面应用的全生命周期
- **AI辅助开发的方法论**：学会了如何有效地将AI编程助手融入开发流程——在调研阶段用于快速理解陌生API，在实现阶段用于加速编码，在调试阶段用于分析错误日志，而非简单地将AI当作代码生成器
- **架构演进意识**：理解了"先让它工作，再让它优雅"的工程哲学，在功能需求和技术债务之间学会了务实的权衡
